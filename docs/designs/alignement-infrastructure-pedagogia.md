## Problem Statement
Stop-Repeat (repo `family-flow`, URL `stop-repeat.tutotech.org`) est actuellement déployé par Coolify en compilant directement le Dockerfile sur la VM de production (8 Go RAM, 4-5 Go swap). Cette compilation sur le serveur a déjà provoqué des saturations mémoire et des pannes de proxy de 15h sur l'infrastructure TutoTech. Par ailleurs, le projet ne bénéficie d'aucun miroir de sécurité GitLab Ultimate (50 000 min/an gratuites inutilisées), Sentry est partiellement configuré dans le code sans injection des secrets ni des sourcemaps en CI/CD, et il manque les garde-fous essentiels éprouvés sur PedagogIA (branche `production`, vérification en ligne `/ready`, rétention du registre).

## What Makes This Cool
L'infrastructure passe d'un déploiement artisanal et risqué sur la VM à un pipeline de niveau bancaire/institutionnel :
1. **Déploiement zéro-charge sur le serveur** : téléchargement instantané d'une image Docker préconstruite sur GHCR en quelques secondes.
2. **Déport des audits de sécurité lourds** : SAST Semgrep, Gitleaks, Gemnasium, Trivy, et DAST tournent sur les 50 000 min/an gratuites de GitLab Ultimate sans consommer 1 seconde de GitHub Actions.
3. **Observabilité totale** : Sentry configuré avec sourcemaps déliées et traçage de version, relayé vers le tableau de bord New Relic associatif.

## Constraints
- Sauvegarder impérativement les minutes GitHub Actions (forfait Team TutoTech partagé).
- Zéro compilation sur la VM Coolify.
- Respecter les secrets Infisical et ne jamais stocker de jeton dans le dépôt.
- Ne pas perturber l'accès Supabase : injecter impérativement `VITE_SUPABASE_URL`, `VITE_SUPABASE_PUBLISHABLE_KEY` et `VITE_SUPABASE_PROJECT_ID` en build-args dans `image.yml` depuis les secrets/variables GitHub (alimentés via Infisical) pour éviter tout repli sur les valeurs de démonstration.

## Premises
1. **Zéro build sur la VM Coolify** : l'image Docker de production doit être construite en amont et publiée sur un registre sécurisé (GHCR).
2. **Arbitrage des quotas** : Stop-Repeat étant une SPA Vite/React (build ~1 min), le build d'image reste sur GitHub Actions avec cache layer `gha` pour une réactivité maximale à chaque merge, tandis que GitLab Ultimate prend 100% de la charge des scans de sécurité lourds.
3. **Alignement rigoureux sur le standard PedagogIA** : réutilisation de la branche `production`, du job de vérification en ligne, du script de nettoyage GHCR (30 images) et du script `deja_teste.py`.

## Approaches Considered
### Approach A: Alignement exact PedagogIA (Recommandée)
  Summary: Build Docker GHCR ultra-rapide sur GitHub Actions (~1 min), déploiement Coolify automatique via branche `production`, scans de sécurité complets déportés sur GitLab Ultimate (50k min), Sentry & New Relic intégrés.
  Effort: M
  Risk: Très faible
  Pros:
    - Réutilise 100% des patterns, scripts et configurations validés sur PedagogIA.
    - Zéro temps de latence au déploiement (pas d'attente du miroir GitLab).
    - Zéro charge CPU/RAM sur le VPS lors du déploiement.
  Cons:
    - Consomme ~1 min de GitHub Actions par fusion sur `main` (négligeable avec cache npm/gha).
  Reuses:
    - `.github/workflows/image.yml` de PedagogIA
    - `.github/scripts/compose_production.py`
    - `.github/scripts/nettoyer_ghcr.py`
    - `.github/scripts/deja_teste.py`
    - `.gitlab-ci.yml` de PedagogIA
    - `scripts/notify-newrelic.py`

### Approach B: Déport intégral du build sur GitLab CI
  Summary: Tout le travail lourd (build Docker + scans) est exécuté sur GitLab CI avec publication sur GitLab Registry et webhook de déploiement Coolify.
  Effort: L
  Risk: Moyen
  Pros:
    - 0 minute GitHub Actions consommée pour les images.
  Cons:
    - Dépendance à un webhook/trigger croisé ou attente de la synchronisation asynchrone du miroir GitLab (5-20 min).
    - Configuration d'un registre supplémentaire (GitLab) dans Coolify.
  Reuses:
    - Templates GitLab CI Docker-in-Docker

### Approach C: Approche progressive / Minimal Viable
  Summary: Activation du miroir GitLab et build GHCR basique sans branche production ni scripts avancés de vérification et de rétention.
  Effort: S
  Risk: Faible, mais laisse une dette technique résiduelle (pas de rollback aisé, accumulation d'images sur GHCR).
  Pros: Rapide à mettre en place.
  Cons: Incomplet et diverge des standards PedagogIA.

## Recommended Approach
Approche A (Alignement exact PedagogIA) : choisie explicitement pour sa robustesse, sa simplicité opérationnelle et son adéquation parfaite avec la stack Vite/React dont le temps de compilation (~60s) ne pèse presque rien sur le quota GitHub.

## Success Criteria
1. Un push sur `main` de `family-flow` déclenche `image.yml` sur GitHub Actions, construit l'image en < 2 min avec sourcemaps transmises à Sentry, la publie sur `ghcr.io/tutotech/family-flow:<commit>`, et met à jour la branche `production`.
2. Coolify détecte la mise à jour de `production`, tire l'image préconstruite sans rien compiler, et relance l'application en < 60s sans pic de charge mémoire sur le serveur.
3. Le job `verifier` interroge `https://stop-repeat.tutotech.org/version.json` et valide la réponse HTTP 200 ainsi que l'exactitude du commit SHA déployé.
4. Le miroir GitLab synchronise le code et exécute automatiquement les 5 scanners Ultimate (SAST Semgrep, Secrets Gitleaks, Dépendances Gemnasium, Container Scan Trivy sur GHCR, DAST planifié) avec 0 minute GitHub consommée.
5. Sentry reçoit les erreurs de production avec sourcemaps dé-obfusquées et releases identifiées.
6. Le job `nettoyer` maintient un maximum de 30 images dans GHCR.

## Distribution Plan
Image de conteneur privée publiée sur GitHub Container Registry (`ghcr.io/tutotech/family-flow:<commit>` et `:main`), consommée par le cluster Coolify de production (`stop-repeat.tutotech.org`).

## Next Steps
1. **Création du miroir GitLab** :
   - Récupérer un jeton GitHub PAT avec droit de lecture de dépôt (`repo:read`) depuis Infisical pour authentifier le pull-mirroring GitLab.
   - Créer le projet privé `tutotech.org/family-flow` via la CLI `glab` (avec le PAT GitLab Infisical).
   - Configurer le pull-mirroring automatique depuis GitHub `TutoTech/family-flow` en utilisant le PAT GitHub.
   - Créer `.gitlab-ci.yml` adapté pour SPA Vite/Nginx avec scans SAST, Secrets, Dépendances, Container Scanning (sur l'image GHCR avec creds), et DAST sur `https://stop-repeat.tutotech.org`.
2. **Configuration Sentry et Supabase** :
   - Créer le projet `stop-repeat-frontend` dans l'organisation Sentry `tutotech` (`de.sentry.io`).
   - Configurer les secrets GitHub (`SENTRY_AUTH_TOKEN`, `VITE_SUPABASE_PUBLISHABLE_KEY`) et variables de dépôt (`VITE_SENTRY_DSN`, `SENTRY_ORG=tutotech`, `SENTRY_PROJECT=stop-repeat-frontend`, `VITE_SUPABASE_URL`, `VITE_SUPABASE_PROJECT_ID`).
3. **Pipeline de déploiement zéro-build (`image.yml`)** :
   - Copier et adapter `.github/workflows/image.yml` depuis PedagogIA.
   - Générer un fichier `dist/version.json` (`{"version": "<commit-sha>", "built_at": "<iso-timestamp>"}`) lors du build Vite pour le healthcheck.
   - Injecter les build-args Supabase (`VITE_SUPABASE_URL`, `VITE_SUPABASE_PUBLISHABLE_KEY`, `VITE_SUPABASE_PROJECT_ID`) et Sentry.
   - Porter les scripts d'assistance : `compose_production.py`, `nettoyer_ghcr.py`, `deja_teste.py`.
   - Créer `docker-compose.yml` de référence dans `family-flow` pointant sur l'image GHCR pour la production.
4. **Bascule Coolify** :
   - Dans Coolify, basculer la source de déploiement de `main` (build Dockerfile) vers la branche `production` (image compose).
   - Configurer le `GHCR_PULL_TOKEN` pour l'authentification.
5. **Tableau de bord New Relic & Surveillance** :
   - Ajouter l'envoi de la télémétrie de sécurité GitLab (`scripts/notify-newrelic.py`) vers le compte New Relic TutoTech.
